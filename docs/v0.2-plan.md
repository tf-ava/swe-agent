# swe-agent v0.2 架构与开发计划

v0.2 先打通一次终端任务：读文件、申请修改、恢复执行、给出回答。随后接入交互控制和扩展。每个阶段按[协作约定](../AGENTS.md)分步审阅。

## 1. 配置、工具与编排

创建 session 时，从 `config.toml` 复制默认配置，随会话保存到数据库。开始一次任务（turn）时，在该 session 的配置上应用本次临时覆盖，得到**本轮有效配置**。它决定用哪个模型、加载哪些指令和工具，以及采用什么审批和沙箱策略。新增配置项随使用它的功能一起实现。

每个工具用一份 `ToolSpec` 写清名称、用途、接受哪些参数、工具元数据和调用入口。比如 `write_file` 的定义里写明它会修改文件，具体写哪个文件、写什么内容，由模型在调用时传入。读写文件的代码放在文件工具里，MCP 工具调用服务的代码放在 MCP 模块里。编排器都通过工具定义里的入口调用它们。

编排器按本轮配置选出可用工具。上下文模块用这份目录生成请求里的 `tools`，编排器也只从这份目录查找模型请求的工具。

| 部分 | 职责 |
| --- | --- |
| 配置与初始化 | 初始化应用数据目录、配置文件和数据库。创建 session 时提供默认配置，开始 turn 时将本次覆盖项应用到会话配置上。 |
| 会话与记忆 | `Session` 描述一个会话，包括它的工作目录、配置和运行状态。`SessionStore` 保存会话、对话历史和摘要，供后续 turn 接着使用。 |
| 上下文 | 根据本轮配置、可用工具和会话历史，构建发给模型的 `messages` 和 `tools`。请求太长时，裁减内容或总结旧历史。 |
| 模型调用 | 按本轮配置及构建的模型可见上下文请求模型，返回模型消息。主对话和历史摘要共用这个入口。 |
| 工具 | 通过 `ToolSpec` 向其他模块提供每个工具的说明、参数定义、元数据和调用入口。各工具负责自己的执行逻辑。 |
| 编排 | 调用上述模块推进 turn，决定工具审批与执行环境，安排新增消息写入、暂停、恢复和结束，向 CLI 报告进展。 |
| CLI | `ask` 提交一次任务或恢复待批调用；`chat` 在同一终端展示进展并接收审批、补充和中断。两者共用编排流程。 |

`TurnRuntime` 放在编排模块，保存本轮有效配置、步数和可用工具。做到运行中控制时再加入输入队列与取消信号。

## 2. 一次 turn 怎么运行

1. **开始。** 编排器读取会话，准备本轮配置、指令和工具，保存用户输入。同一 session 一次只运行一个 turn。
2. **请求模型。** 上下文模块用本轮指令、可用工具和最新历史构建请求。编排器调用模型，保存回复和用量。
3. **处理回复。** 模型直接给出回答时，如果没有新的用户补充，本轮就结束。模型要求调用工具时，编排器按顺序处理：根据工具元数据、本次参数和本轮配置，决定是否执行、是否需要审批，以及在哪里执行。每次调用的结果或失败原因都带上原调用 ID 写入历史。处理完这批调用，就回到第 2 步。达到步数上限或运行失败时，说明原因并结束本轮。

**审批。** 工具需要批准时，编排器在执行前保存进度，暂停这个 turn，释放本次执行占用的资源。本轮的临时配置只随这次任务恢复。`ask` 显示待批工具和参数后退出，`chat` 显示同样的请求后回到输入提示符。收到决定后，两者都从同一 turn 的待批调用继续。批准就用展示过的参数执行；拒绝就记下结果，跳过这批剩余调用，再问模型。

**补充和停止。** `chat` 收到的补充会随下一次请求发给模型。即使模型刚给出回答，这期间已收到的补充也要在本轮处理。用户要求停止时，编排器停止发起后续调用，尽可能取消当前模型请求或终止子进程。保留已收到的输入和已完成的结果，未开始的调用记为跳过。如果写文件时程序退出，无法确认是否写入，就记为“结果未知”，下次打开会话时不要自动再写一次。

## 3. 模型能看到什么

上下文有两类来源：

- **本轮准备的内容。** 编排器按有效配置准备系统提示词、会话工作目录、带来源的项目指令、skill 简介，以及已启用的内置和 MCP 工具定义。首版可先用固定系统提示词。工具定义通过请求的 `tools` 字段传入。
- **会话积累的内容。** 每次请求读取已有摘要和摘要之后的消息，带上最新的工具结果和用户补充。原始历史记录实际对话和执行结果。下一轮更换提示词或工具时，只需重新准备本轮内容。

按实际要发送的内容估算长度，给模型的回答留出空间。请求太长时，先缩短较早的大工具结果，留下结论和原消息 ID。仍然太长，再把旧摘要和接下来的一段历史一起总结。保留当前任务和最近的补充。一次模型回复里的工具调用和对应结果要放在一起。

原文始终可查。新摘要生成成功后，才记录它总结到了哪条消息。失败时沿用旧摘要和原来的读取位置。上下文模块会向编排器说明压缩失败或必要内容仍然过长的原因。

## 4. 扩展模块

| 扩展 | 向核心提供什么 | v0.2 范围 |
| --- | --- | --- |
| 项目指令 | 带来源路径的文本 | 只读取 session 工作目录中的 `AGENTS.md`，限制读取长度，将内容和来源路径交给上下文模块。 |
| Skill | 简介和 `load_skill(name)` 工具 | 从配置的 skills 目录发现多个技能。每个技能一个子目录，以 `SKILL.md` 为入口，也可以放示例、脚本和参考资料。先给模型名称和简介，用到某个技能时再读正文。 |
| 命令沙箱 | 在 Docker 中执行命令 | 指定挂载哪些目录、是否允许联网，命令超时或取消时清理容器。启用 Docker 后，Git 和 `rg` 也在容器里运行。Docker 不可用就报错。在宿主机上读写文件的工具自行检查路径和读写权限。 |
| MCP | 把服务提供的工具加入本轮工具目录 | 首版按配置的服务地址，通过 Streamable HTTP 连接，列出工具并注册为带服务名前缀的 `ToolSpec`。暂停或结束时关闭连接，恢复时重连并核对待批工具。后续在同一模块补本地 stdio 支持。 |
| 子 agent | 委派工具，返回子任务结果和子 session ID | 父 agent 通过工具交代任务和必要背景。工具为子 agent 创建独立 session，复用现有编排器执行任务。父 agent 收到结果后继续工作。首版只读，限制子 agent 数量，只允许委派一层。父任务取消时，正在运行的子任务也一起取消。 |

## 5. 开发阶段与验收

| 阶段 | 实施与验收 |
| --- | --- |
| **1．配置与存储（已完成）** | 完成应用初始化、三层配置和会话持久化。用户可以创建和查询 session、修改配置，后续 turn 可以继续使用已保存的会话。 |
| **2．工具（已完成）** | 把每个内置工具的说明、参数定义、元数据和调用入口集中在一份 `ToolSpec` 里，供其他模块使用。先迁移 `read_file` 和 `write_file`，用真实读写验证这套定义，再迁移其余工具。 |
| **3．模型与上下文** | 接通模型调用，按本轮配置把系统提示词、项目指令、可用工具、摘要和最近的对话组成一次请求。内容太长时，先缩短较早的工具结果，再按需总结旧历史。验收时查看压缩前后的请求，确认只列出本轮启用的工具，当前任务、最近补充以及保留的工具调用和对应结果都能一起读到。 |
| **4．编排与 `ask`** | 让一次 turn 从提问走到最终回答。编排器取得本轮配置，请上下文模块准备请求，再调用模型、执行工具并保存结果。用 `ask` 完成“读一个文件并回答问题”，再用写文件任务验证审批、拒绝和恢复。 |
| **5．`chat` 与控制** | 让用户在同一个终端看见进展、补充要求、处理审批或停止任务。例如在长命令运行时中断，确认子进程退出，已完成的结果仍可查看。 |
| **6．接入扩展功能** | 按扩展表逐项接入并从正式 CLI 验证，最后做整体验收。 |

`history` 查询可放在阶段 4 验收前，便于核对漏记或重复执行。session 删除单独安排，处理活跃和待审批的会话。
